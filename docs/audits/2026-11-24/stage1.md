## Допуск к разрушающим тестам

`api/tests/helpers.ts:4–7` задаёт DSN и каталог фото через `??=`: унаследованные
значения имеют приоритет. `helpers.ts:26` выполняет
`DROP SCHEMA public CASCADE; CREATE SCHEMA public`.
Порт, имя БД и её прежнее использование сами по себе не доказывают безопасность.
Существующие `site2-db`, `site2-api`, `apixspb2-test-db` и найденный ранее
`site2-review-20261124` для тестов не использовались и не переключались.

До первого API-теста доказано:

1. Созданы новая Docker-сеть `--internal` и новый контейнер PostgreSQL из локального
   неизменяемого image ID. Нет опубликованных портов и общих volumes/bind mounts.
2. Данные PostgreSQL — новый `tmpfs` `/var/lib/postgresql/data`; `Mounts=[]`.
   SQL вернул `current_database=apixspb_test`, `current_user=postgres`,
   `user_table_count=0`, system identifier `7711494481293959209`.
3. Тестовый runtime использует только сетевое пространство этого контейнера,
   `--read-only`, `--cap-drop ALL`, `no-new-privileges`, отдельный uid и `tmpfs /tmp`.
4. Read-only mounts ограничены `api/src`, `api/tests`, `api/node_modules`,
   `api/package.json`, `api/tsconfig.json` и `web/src/dateFormat.ts`.
   `.env`, домашние ключи, Docker socket, дампы, живые фото и пользовательские
   каталоги в runtime не монтируются.
5. `env -i` задаёт только тестовый DSN/JWT, `NODE_ENV=test`, `TZ=UTC`, отдельный
   `PHOTO_DIR=/tmp/site2-audit-photos` и loopback-заглушки внешних endpoint.
   Настоящие учётные данные и боевой дамп не используются.
6. Запускается тестовый `buildServer()` + `app.inject`, а не production entrypoint.
   Планировщики iVend, ежедневной сводки и очистки фото не включаются;
   relay/OCR/backup/sync и systemd timers не запускаются этим контуром.

Internal-сеть закрывает обычный выход в интернет, но не является универсальным
firewall от Docker gateway/хоста. Поэтому отсутствие настоящих credentials,
узкие mounts и фиктивные внешние адреса — отдельные обязательные меры.

Неизменяемые образы первого прогона:

- PostgreSQL: `sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685`.
- Runtime с Node/ffmpeg: `sha256:f43e5927a6f4581047fd8acc69bbe17539d5b49be1f948084f6afccb47085113`.

Сохраняемый runner дополнительно фиксирует SHA-256 исходников до/после,
проверяет точный allowlist mounts, окончательное состояние контейнера и ошибки
очистки. Он всегда обращается к локальному Unix Docker socket и удаляет только
полученные при создании ID. Временные ресурсы первого полного прогона создавались
предварительной `/tmp`-версией с теми же командами запуска тестов; финальный runner
отдельно проверен в режиме preflight. Полный лог и доказательства первого прогона
сохранены локально; сырые логи в Git не добавляются.

## Воспроизведение

Требования: локальный Docker, уже имеющиеся `postgres:16-alpine` и `2-api:latest`,
установленные зависимости `api/node_modules`. Образы автоматически не скачиваются;
`2-api` нужен как runtime Node + ffmpeg, исходники берутся из read-only checkout.
Сначала выполнить из корня репозитория:

```bash
python3 scripts/review-isolated-api-tests.py --preflight-only
python3 scripts/review-isolated-api-tests.py
```

Первая команда проверяет контур, TCP-подключение к новой пустой БД, `tsx` и `ffmpeg`.
Вторая запускает все `api/tests/*.test.ts` последовательно и возвращает код тестов.
Каждый запуск печатает уникальный каталог `/tmp/site2-audit-…/` с `isolation.json`
и `api-tests.log`. БД, фото и сеть удаляются после запуска, включая неуспешный;
ошибка очистки даёт ненулевой результат. Новая проверка начинается с нового кластера.

Успешный preflight финального runner: Node `v22.23.2`, ffmpeg `8.1.3`, тестовая БД
`apixspb_test`, пользователь `postgres`. Локальные инструменты: npm `10.9.8`,
TypeScript API/web `5.9.3`, tsx `4.23.13`, Vite `6.4.3`.
Python OCR-тесты запускались через существующий
`/home/s/.local/share/site2-ocr/venv/bin/python` с заглушками API и subprocess.
Системный Python не содержит `cv2`; это ограничение окружения, а не дефект OCR.

## Подтверждённые проблемы baseline

### T1 — P2: тест закрытия дня противоречит текущему месячному правилу

- Файлы: `api/tests/day_close.test.ts:140,171,206`; фикстуры
  `:57,106,153` используют `2026-09-10`.
- Условия: запустить suite в ноябре 2026 либо другом месяце вне сентября 2026.
- Ожидание теста: сентябрьские данные возвращаются через `/api/day-close/mine`
  и `/api/day-close/other`; дальнейшая проверка удаления берёт первую строку.
- Факт: оба списка пусты; assertions получают `0 != 1`, `0 != 2`, затем
  `TypeError` при чтении `target.id`. Три тестовых сценария падают.
- Основание: DECISION-109 и `api/src/commands/dayClose.ts:183–227` ограничивают
  списки текущим календарным месяцем. Запись и хранение прошлых дат этим правилом
  не запрещаются. Это подтверждённый дефект актуальности тестов, не потеря расходов.
- Исправление отдельным шагом слоя тестов: даты текущего месяца в сценариях
  видимости/удаления, отдельные assertions исключения предыдущего месяца и проверки
  границ месяца. Не расширять выдачу API ради старых assertions.

### T2 — P2: тест XLSX остался на предыдущем формате генератора

- Файл: `api/tests/expenses.test.ts:153–172`, первое падение `:158`.
- Воспроизведение: полный API baseline на пустой тестовой БД;
  `buildMonthlyReportWorkbook` → проверка восьми заголовков секций.
- Факт: `не хватает блоков: 8,-1,-1,18,29,-1,40,51` — три ожидаемых блока отсутствуют.
- История: `3ed56be` от 04.11.2026, `simplify monthly Excel layout and retain
  three-service ROI`, удалил секции counts/groups/rent и строку profit,
  перенёс ROI с девятого столбца на седьмой. Тест секций остался от `843fd91`,
  ROI assertion — от `edd2438`. Текущие пять секций видны в
  `api/src/domain/monthlyExcelReport.ts:207–211`, ROI — `:158,168`.
- Это подтверждённая несогласованность теста с более поздним изменением реализации.
  Соответствие сокращённого формата требованиям владельца ещё нужно сверить на
  этапе 2; вывод об ошибке денежных итогов по этому падению не делается.
- Исправление: сначала подтвердить действующий формат, затем обновить assertions
  секций, profit/ROI и независимо проверить суммы, не ограничиваясь заголовками.

- Очереди `outbox/taskOutbox/dayCloseOutbox` не содержат ownerId, logout их сохраняет;

Очередь следующих работ: сначала сверка решений по деньгам, историческим настройкам
и видимости; затем независимые финансовые/конкурентные примеры, матрица доступа,

доступа/потери/денег должны опережать прочие исправления. T1/T2 — отдельные задачи
согласования и актуализации тестов; существующее поведение ради зелёного baseline
не меняется. Все продуктовые исправления требуют собственного доказательства,
описания затронутых слоёв и соблюдения правил проекта о многомодульных изменениях.

На этом этапе не подтверждены новые продуктовые дефекты. Это граница выполненной
проверки, а не заключение об отсутствии дефектов. Архитектурные замечания
(дублирование типов/расчётов, крупные модули, отсутствие браузерного runner)
остаются отдельными наблюдениями и не смешиваются с пользовательскими ошибками.
