# Постоянные предпочтения пользователя

- Все завершённые изменения исходного кода обязательно сохранять в GitHub: делать осмысленные коммиты и push в `origin`. Обычный push разрешён пользователем и не требует отдельного подтверждения.
- Изменения, применённые локально или напрямую на проде, также должны попадать в GitHub. Не считать работу завершённой, пока push не подтверждён; если он заблокирован, явно сообщать об этом.
- Не включать в коммиты секреты, локальные учётные данные, дампы базы, пользовательские данные и посторонние незавершённые правки. Не применять force push без явного разрешения.
- При изменениях учитывать существующие инструкции проекта в `CLAUDE.md` и `.claude/rules/modularity.md`; явные инструкции пользователя имеют приоритет.

## Память и навигация

- В начале задачи читать `docs/memory/START.md` и короткий `docs/memory/CURRENT.md`.
  Затем `node scripts/memory.mjs topic "тема"`: точки входа, решения, тесты.
- Если путь неизвестен: `node scripts/memory.mjs find "имя или маршрут"`;
  перед чтением большого файла — `node scripts/memory.mjs outline путь/к/файлу.ts`.
  Читай нужные определения и непосредственных потребителей, не весь проект.
- Историю извлекать адресно: `search "текст"`, затем `decision NNN` через тот же скрипт.
  Не читать `DECISIONS.md` целиком. Проверять область известных уточнений; их список неполон.
- Новые решения/уточнения, карту тем и краткое состояние обновлять вместе с изменениями.
  Перед передачей/сжатием сохранять следующий шаг и доказательства; чужие активные задачи не стирать.
- Проверки памяти: `node scripts/memory.mjs check` и `node --test scripts/memory.test.mjs`.
  Они не доказывают бизнес-корректность. Тесты API пересоздают схему: сначала доказать,
  что БД отдельная тестовая; не использовать базу локального сайта по совпадению порта.
